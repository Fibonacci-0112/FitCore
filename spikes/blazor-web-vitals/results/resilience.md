# Faults mid-session

Output of `node resilience.mjs 1` on 2026-10-13, 1 run(s) per row. Each run loads the Today screen through `proxy.mjs` (50 ms RTT), saves one entry, starts the fault, taps "Add banana" 1 s into it, and after the fault taps "Add banana" again.

- **Dead zone:** nothing gets through, then everything queued is delivered, as when a phone loses signal and TCP retransmits. **Network switch / offline:** every connection is reset and new ones are refused, as when a phone changes network.
- **Server restart:** the server process stops and a new one starts 3 s later on the same port, as in a deploy. The diary data survives (a file stands in for the database); circuits don't. "State in Redis" uses .NET 10 circuit state persistence with a Redis `HybridCache`.
- **Tap during the fault:** what the member saw after the tap 1 s in (times from the tap, in ms), and whether the server had stored it once the page was usable again and 5 s had passed. A tap that landed on the reconnect UI never reached the button.
- **Reconnect UI:** what Blazor showed over the page, and for how long. **Usable again:** from the end of the fault until no reconnect UI covered a ready screen.
- **Error banner:** whether Blazor's error banner appeared at any point. It sits along the bottom of the page and doesn't block taps, so it doesn't count against "Usable again".
- **Next tap:** one more "Add banana" after that, and whether it saved. **Reloads:** full page reloads.
- **Bananas shown / stored / tapped:** rows on screen at the end, entries the server stored, and taps that reached the button.
